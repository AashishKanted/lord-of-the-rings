# Advaitic — Robotic Systems Assignment

Build a repeatable mobile manipulation system for a moving assembly line.
We want to see how you turn a customer workflow into a working system, measure it,
and recover when things go wrong.

## The customer workflow

A kit carries a bottle and a separate rigid ring along a moving conveyor. Pick up
the ring and place it over the bottle neck, seated on the shoulder. A downstream
inspection system decides whether it is acceptable. The mobile robot completes
**five accepted assemblies at station A**, stows its arm, navigates to station B,
and completes **five accepted assemblies there**. Attempts and robot completion
messages do not count as accepted assemblies.

Use one arm on an AMR by default. Choose a documented mobile manipulator and verify
its reach and collision clearance in this cell. Bimanual manipulation is unnecessary.
MuJoCo is recommended; another simulator is acceptable if it runs locally and
reproduces the same tests.

## Targets

| Item | Requirement |
|---|---|
| Nominal belt speed / kit pitch | 30 mm/s / 450 mm: one arrival every 15 s |
| Assembly cycle | At most 12 s from bottle entering work zone to a verified 0.5 s released seating hold |
| Working window | 600 mm: 20 s at nominal speed |
| Nominal mission | Five accepted at A, then five at B, within 270 simulated seconds |
| Human interruption | Stop command within 200 ms; motion settles within 1 s; explicit recovery |
| Integration fault | Recover an ambiguous PLC acknowledgement without double counting |

These are proposed synthetic customer requirements. The 12 s target has a sizing
budget, not a completed robot benchmark. Report simulated time and real wall time
separately. Fault runs have a 360 s simulation limit; their interrupted cycles are
reported separately rather than silently omitted from the nominal average.

## What you may simplify

Use a known map and existing planners, IK, controllers, and robot models. State
estimation still needs to consume simulated sensors; document noise and latency.
A procedural conveyor, simple kit, retained bottle, and primitive assets are fine.
A belt may be implemented by driving a carrier along its track. The ring must be
a free rigid body when released; it cannot be carried by an invisible script.

A documented grasp constraint is allowed to keep the task practical: activate it
only after the gripper reaches a valid grasp pose and closes, disable it on release,
and retain collision checking. Do not snap a distant object into the gripper or
onto the bottle. Show the constraint and its activation conditions in your report.

Known station goals and a state machine are normal engineering. Direct object
pose writes to create success, teleporting the robot, replaying one trajectory
regardless of observations, bypassing inspection, or hand-editing evidence are not.
We judge a repeatable system and your understanding of it. Code generated by an
agent is acceptable; an unexamined script that only works for one recording is not.

## Run the starter

Python 3.11+; `uv` is convenient but not required.

```sh
uv sync --group dev --group physics
uv run pytest -q
uv run systems-timing
uv run python -m advaitic_systems.parts --write-xml assets/parts_fixture.xml
uv run systems-plc --port 1502
```

The standalone PLC has no live plant attached. Use the embedded server pattern in
the interface document to connect your simulator. After producing real evidence:

```sh
uv run systems-check results/nominal-seed-0/events.jsonl --scenario nominal
uv run systems-check results/human-stop/events.jsonl --scenario human_stop
uv run systems-check results/plc-retry/events.jsonl --scenario plc_retry
```

The checker catches inconsistent logs. It does not prove that fabricated logs came
from physics. We also rerun your simulator and inspect the measurement bridge.

## Submission

Share your solution repository URL and pinned commit directly with Advaitic, with
one setup command and one command per evaluation. Include raw logs, summary metrics,
a short demo, architecture, failure analysis, and asset and tool provenance. Do not
submit your solution as a pull request to this starter: that exposes it to other
candidates. To keep it private, clone the starter into a private repository and
grant Advaitic access.

Keep the evaluation and customer specification unchanged; propose corrections
separately. Candidate code belongs in your own modules/configs. We will discuss
your implementation, measurements and failures in a technical deep dive.
